blocks full run1. Approve the benchmark approach, then the full Luna run

You asked to review the approach first. It is set out in model-gating/benchmark/README.md; the main points:

  • The model gets the gold claim list. Each run receives the claims to check: wording, location and printed value, but no verdicts. When Luna picked its own claims (batch 1), it addressed only 11 of 27 gold claims and never listed the planted claim on T-06. Scores then measured claim selection, not reproduction. With the list (batch 2), all 26 were addressed.
  • Prompt. The public prompt word for word, except for a slim bundle: certificate, executed code, logs and environment record.
  • Isolation. A fresh folder outside the repository per target, with network access open and an instruction not to read existing reports. Twins are rebuilt locally from hash-pinned inputs, and nothing names them as twins.
  • Configuration. gpt-6-luna through the Codex CLI on your ChatGPT subscription, at the default (medium) reasoning effort.

Recommendation: approve and run the remaining 33 targets. At 2 to 10 minutes each, five at a time, that is about an hour on the subscription. Score claim selection separately later.

2. Does switching on an option the authors document count as a justified fix?

G-21's printed AICs (410, 497, 507) come from a mixed-effects variant that the authors' script describes in a comment but does not run. Run as shipped, the script gives 463, 570 and 785. Gold labels these claims match, following the I4R reproducer. Luna called them discrepant, which is defensible because rule pack 1.1.0 only allows fixes that leave the analysis unchanged. These three claims are Luna's main errors in batch 2.

Recommendation: no. Switching to a different model specification is a change of analysis even when a comment describes it. G-21 C3 to C5 would become discrepant (P2), and the printed values stay recorded as diagnostics. This needs Sol's agreement before I change gold.

3. May a model run the statements after a crash that they do not depend on?

On G-23 the script stops on a missing object. Two later statistics do not use that object: C3 recurs, and for C4 the paper prints 1037.5 where the code gives 1137.5. Reaching them means skipping the failing statement. Luna stopped at the crash and called both not_checkable.

Recommendation: yes, as a justified fix. It is the same kind of change as running scripts in the right order, provided the skipped statement feeds nothing the claim uses. I would add this to rule pack §3.

4. Blinded recreation needs its own benchmark

The gold set and prompt cover computational reproduction only. Blinded recreation, where the model rebuilds the analysis from the paper without the code, needs a separate prompt, a rule that hides the code, and scoring against the same printed values. The 30 papers could be reused: their packages exist, and the gold says which numbers are recoverable at all.

Recommendation: build it on the same 30 papers after the full Luna run. Tell me if the pipeline group already has a recreation prompt I should start from.

5. Add Stata papers to the gold set

With direct translation now allowed, Stata packages become eligible. That is the main route to more technical-failure cases and more economics. The current pool holds only three Stata candidates, because screening filtered Stata out early, so this needs a new screening round of I4R and REPRO-Bench Stata packages. Each paper then needs the full double-labelling and reconciliation cycle with Sol.

Recommendation: after the full Luna run, add 10 Stata papers (G-31 to G-40), labelled the same way, and test whether translation works at all before scaling up.

What "transparent recreation" meant

In the pilot, two models could not get a number from the shipped code. They then wrote or changed code themselves until it gave the printed value, said so in a note, and still labelled the claim match. Under your framing that is simply "does not reproduce", and the new rule pack and basis field say so explicitly. Luna did not do this once in either batch: I read every fix and note it wrote, and its fixes were paths, package installs, a figure-label loop, a column alias and stubbing out View().

A related finding: in batch 1, Luna spotted T-02's planted change by comparing the patched script with the authors' rendered output, which still shows the original value. Twins whose packages include rendered outputs can therefore be caught by comparison as well as by execution. Before the full run I would strip rendered outputs from twin packages, or accept that as a legitimate way of finding the error.

I4R: nothing to report

I checked every gold claim where our labels contradict a human report. All discrepancies but G-08's came from the reports themselves. Rereading the article, rerunning the shipped estimators and Sol's independent review all showed that the two G-08 "errors" were our misreading. G-11's I4R table differs from the article by a few thousandths while calling the reproduction perfect. The authors' own log matches the article, so this is a rerun difference, not an error to report. One finding concerns CODECHECK rather than I4R: on G-23 the shipped code does compute two statistics that the CODECHECK notes treated as blocked, and for one of them the paper prints W = 1037.5 where the code gives 1137.5.
