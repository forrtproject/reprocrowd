# Specification review, Sol, round 1

## Summary

I agree with the settled design decisions. I do not yet agree to freeze the projected gold or use the proposed headline score for ranking. The main blockers are unsupported variation labels, inconsistent treatment of source-identified typos, a headline that checks statuses without establishing successful reproduction, and isolation rules that rely on an agent's compliance. These concerns follow directly from the evidence requirements and scoring definitions in `model-gating/benchmark/SPEC.md:95-138,181-204,208-233,278-282`.

This review checked every gold record's statuses, references, tolerances, and explanatory fields. I also read the previous reconciliation and R10 review, downloaded the relevant public reports into memory, visually checked the G-22 and G-28 report tables, and inspected selected pinned scripts. I did not run full analyses. No personal email address was sent to an external service. All file citations below are repository-relative, with line numbers. Recommendations and proposed rules are explicitly distinguished from observed evidence.

## Section 1: what the benchmark measures

**AGREE with the tracks, the end-to-end objective, and the diagnostic decomposed mode. DISAGREE with the correspondence between that objective and section 6.** Section 1 requires identifying, reproducing, and judging claims, but the headline currently rewards only identification and the status string; paper judgement is expressly outside it (`model-gating/benchmark/SPEC.md:8-24,211-224`). A model can therefore obtain headline credit with a correct status and an incorrect recomputed value, an invalid analytical basis, or a wrong paper outcome.

Proposed replacement:

> Each track has one headline score for the complete check. A must-check result earns credit only when it is identified, its computation or inability to compute is supported by the required evidence, its basis and fixes are admissible, and its status is correct. Paper judgement is assessed within the complete-check score under the aggregation rule in section 6. Decomposed scores use the same evidence and judgement criteria but supply the must-check list; they are diagnostic and are not used for ranking.

This preserves the settled single score per track. Section 6 below specifies an aggregation that implements it.

## Section 2: targets and Track B

### Section 2.1

**AGREE with code-level twins being Track A only and with stripping rendered outputs. DISAGREE with the claim that the presentation is necessarily blind.** Twins receive local packages, while ordinary gold targets currently receive remote package URLs; the local path itself contains the twin identifier. That exposes a condition cue even without an explicit statement that a target is a twin (`model-gating/benchmark/run_codex.py:44-56`). The stripping rule deliberately retains analytical input data, including intermediates generated by scripts, so stripping is not an assurance that all retained files are free of old results (`model-gating/gold-set/twins/strip_outputs.json:2`).

Proposed replacement:

> Build all targets through the same packaging interface. Give models opaque target identifiers and local paths with identical structure, whether the target is an original or a twin. Keep the original/twin relation and stripping manifest in evaluator-only metadata. Inspect retained input objects for cached analytical outputs and define explicitly which deposited intermediates remain authorised inputs. Prohibit replacing the supplied package with an upstream copy in either condition.

A target's article and code can still reveal inconsistencies. Blinding should mean withholding evaluator-created condition cues, rather than promising that a careful reader cannot suspect a planted change.

### Section 2.2

**AGREE that Track B is feasible for an eligible subset. DISAGREE that the current eligibility and leakage controls are sufficient.** Eligibility merely requires that the article describe the analysis, while section 5 anticipates value-changing ambiguities. Keeping a README verbatim can also keep code fragments or results: the draft itself authorises keeping that document while prohibiting authors' code and cached results (`model-gating/benchmark/SPEC.md:47-55,200-204`). This needs a content rule, not an extension-based deletion rule.

Proposed replacement:

> Define eligibility per claim and publish the resulting paper and claim denominators before evaluation. A paper may enter when its retained claims have usable deposited data and a prespecified reconstruction starting point. Record whether those inputs are raw observations or deposited processed data, their provenance, permitted preprocessing, and any unavailable upstream steps. Require a content audit of every retained file, including README text, codebooks, spreadsheets, R objects, notebook metadata, archives, hidden files, formula cells, caches, and serialised model objects. Keep documentation needed to interpret the data, but remove author analysis code, computational recipes that amount to that code, and stored analytical outputs. Record all removals and any loss of methodological information.

The processed-data boundary matters in this set: G-29 explicitly starts some claims from deposited processed inputs, and G-16 starts from supplied contextual probabilities (`model-gating/gold-set/gold/G-29.json:151-177`; `model-gating/gold-set/gold/G-16.json:141-145`). A Track B result from such inputs must not be described as recreation from raw data.

> Download and pin the article, supplement, and permitted methodological documents before the run. Freeze the documentary corpus. Obtain dependencies through an evaluator-controlled package mirror or proxy. Run with no access to upstream study repositories, reproduction reports, previous runs, host files, or credentials. Record network activity outside the model's control. Distinguish a blocked request from successful retrieval; a forbidden attempted retrieval can be a protocol violation, but a harmless article request redirected through a DOI is not automatically a code fetch.

Checking only requests to the package repository or DOI, as proposed, does not cover raw-file hosts, mirrors, search snippets, supplementary downloads, redirects, or encoded shell requests. It can also misclassify a permitted article DOI fetch (`model-gating/benchmark/SPEC.md:53-55,228-230`). Open internet access is therefore incompatible with a strong claim that Track B is code-blind unless external access is mediated.

## Section 3: claim identification

**AGREE with recall of a must-check subset as a development measure. DISAGREE with treating it as complete claim-identification quality.** The lists were chosen from results assessed by a human source, rather than through an independent exhaustive definition of the paper's key claims (`model-gating/benchmark/SPEC.md:61-67`; `model-gating/gold-set/README.md:43-48`). A model can reasonably choose important unlisted findings and still have low subset recall. Conversely, copying every table cell can maximise recall without selecting the findings on which the paper rests.

Proposed replacement:

> The primary identification measure is recall of a frozen assessed subset, not recall of all important claims. Freeze the article corpus, the claim-selection rubric, and must-check targets before testing a candidate pipeline. Each must-check target must have an article-grounded scientific referent, not merely a number and an exhibit. Record why it belongs in the subset. Audit legitimate extra claims separately; do not count a scientifically valid extra claim as false merely because it is absent from gold.

The end-to-end benchmark remains defensible with this narrower interpretation. A broader claim-selection benchmark would need independent coverage annotations. Gold changes suggested by development runs must be versioned before further comparisons, rather than silently changing the evaluation target; the existing gold already records versioned corrections (`model-gating/gold-set/README.md:53-67`).

### Atomic results and mapping

**DISAGREE with the mapping rule as a sufficient identity contract.** An exhibit can contain the same printed number for several variables, models, groups, or waves. The draft makes printed value and exhibit sufficient and resolves ties by proximity (`model-gating/benchmark/SPEC.md:76-81`). This can map the wrong scientific result. The current implementation is even looser: it treats all gold numbers appearing somewhere in the submitted string as a match, allows rounding-sized differences in the *reported* value, and need not require any exhibit overlap (`model-gating/scripts/score_certificate.py:35-58,69-95`).

Read-only probes of those functions returned `True` for `same_reported('< .01', '.01')`, for `same_reported('0.05', '0.054')`, and for an interval embedded in a longer list containing an unrelated extra number. The parser reads `.17` as `17` and treats the separator in `53.6–56.2` as a minus sign. These observations follow from the regex and normalisation at `model-gating/scripts/score_certificate.py:46-58`; they are implementation defects to prevent in the new contract.

Proposed replacement:

> Give every result a stable `result_id` and parent `claim_id`. Its identity includes the study, population or subgroup, outcome, predictor or contrast, model specification or column, wave, statistic, and exhibit location where applicable. Map on scientific identity and article location; use the printed number as a consistency check. Normalisation preserves signs, inequality operators, interval endpoint order, units, and printed precision. It may standardise equivalent typography and explicit unit conversions, but it does not introduce numerical tolerance into the article transcription. Use a one-to-one assignment. Audit unmatched near-misses and genuinely ambiguous identities without seeing the candidate's status or recomputed value, and retain the adjudication.

Section 3.2 also needs a migration rule. G-27 C1-C5 each combine six numeric columns, while G-08 C6 carries a coefficient plus a separate `reported_p`; neither is yet a complete atomic gold representation (`model-gating/gold-set/gold/G-27.json:259`; `model-gating/gold-set/claims/G-08.json:62-68`). Split these into result IDs and freeze the denominator and grouping policy. An interval remains one result with two separately typed endpoints, as settled in the draft (`model-gating/benchmark/SPEC.md:69-72`).

## Section 4: statuses, basis, and outcomes

### Section 4.1

**AGREE with rounding convention as the only match tolerance. DISAGREE that the present definition is mechanically complete.** It specifies decimal places and a relative half-boundary allowance, but does not define the reference scale for that allowance, scientific notation, negative ties, trailing zeros, units, or rounded counts (`model-gating/benchmark/SPEC.md:95-102,114-117`). These are active cases: G-03 prints scientific-notation p values, G-15 prints percentages, and G-20 C3 spells out a count as “five” (`model-gating/gold-set/gold/G-03.json:32-50`; `model-gating/gold-set/gold/G-15.json:120-151`; `model-gating/gold-set/gold/G-20.json:76-95`).

Proposed replacement:

> Preserve the exact printed token and parse it into a typed comparison. Store `kind`, `operator`, decimal value or ordered endpoints, unit, scale, and rounding quantum. Infer precision from the printed token, including trailing zeros and scientific notation. Convert the recomputed quantity into the printed unit before comparing. For a scalar, `match` means that decimal round-half-up, defined as ties away from zero, or round-half-even at that quantum produces the printed token's numeric value. For an interval, both ordered endpoints must match at their own printed precision. Exact counts are compared as integers, including counts written as words. A rounded or approximate count must be explicitly identified as such and adjudicated before inclusion.

> For the floating-point boundary allowance, let `q` be the printed rounding quantum. Only a recomputed value within `1e-9 * q` of a rounding half boundary is treated as exactly on that boundary. Perform the comparison using decimal arithmetic or an equivalent documented representation. Do not scale this allowance by the magnitude of the statistic, apply it around an inequality threshold, or apply it to exact counts.

Scaling by the statistic's magnitude would permit an allowance many printed units wide for sufficiently large values. Scaling by `q` makes this a narrowly defined rounding-boundary convention. Also, `.125 = 1/8`, which is binary `0.001`, so that decimal literal is exactly representable in binary; the draft's example should describe a computed result near a half boundary rather than storage of that decimal literal (`model-gating/benchmark/SPEC.md:99-100`).

> Preserve `<`, `<=`, `>`, and `>=` and compare an unrounded recomputation with the stated bound. An equality p value is a rounded scalar; an inequality p value is a bound, not a rounded equality. Do not silently replace a printed zero p value with an inequality. Validate p values against their domain, preserve whether they are adjusted and by which method, and record the relevant sidedness and degrees of freedom. An interval records its type, coverage, and null value on its scale. Percentages and proportions are equivalent only after an explicit scale conversion; a percentage-point effect and a relative percentage change are different quantities.

The inferential veto also needs precedence. A rounded equality can match while the unrounded p value and a stated decision fall on different sides of a threshold. Keep the numerical result and the paper's inferential assertion separate, or state explicitly that the veto overrides `match`; the current text says only that vetoes precede `close` and also apply to `within_variation` (`model-gating/benchmark/SPEC.md:101,114-117,138`). I recommend separate assertion records so that faithful numerical transcription is not relabelled inconsistently.

### Section 4.2

**AGREE with requiring a supported reporting slip and with the settled substantive vetoes. DISAGREE with the ambiguity of “one named slip”.** The source-identified-typo allowance is broad enough to include a misprinted interval, but section 5 rejects G-22 C3 simply because both endpoints differ. The report identifies the intercept and its interval together in its typo discussion ([G-22 report](https://osf.io/download/6a8dab91bef1626ff08e0770/), PDF p. 4; `model-gating/benchmark/SPEC.md:106-117,194`).

Proposed replacement:

> A named slip is a specific documented reporting transformation or a specifically located source-identified transcription error. State its affected result or linked results, evidence, and corrected values. For truncation or transposition, demonstrate the transformation and its inverse; numerical proximity alone is insufficient. For a source-identified typo, the source must identify the particular affected entry and provide a supported correction. A whole interval or a copied row can be one reporting error even when several digits or endpoints differ. The sign, null-inclusion, inequality, threshold, and exact-count vetoes still apply to every affected result individually. A generic statement that a paper contains typos does not establish the cause of every difference.

The draft removes the previous numerical ceiling for `close`; that ceiling remains in the current rule pack (`crowd-repro/RULEPACK-v1.1.0.md:109-117`). I accept reviewing the new rule on its own terms, but section 5 must apply it consistently to G-07 and G-15 as well. If the intention is to retain a size restriction, state it explicitly and recompute the migration; do not retain it implicitly for selected records.

### Section 4.3

**AGREE with the separate status for analyses that are not exactly reproducible. DISAGREE with the present evidence and precedence rules.** A seed plus an unspecified environment is not proof of a changed RNG stream, a changed package algorithm, or irreducible optimiser variation. The draft also requires different seeds even for deterministic package-version changes and parallel-order effects, where changing seeds does not test the named cause (`model-gating/benchmark/SPEC.md:124-138`).

Proposed replacement:

> Distinguish a potential source of variation, evidence that the target result actually varies, and evidence that the observed gap is consistent with that variation. Record the original and attempted environment, RNG kind and state or seed placement, execution order, parallel settings, relevant algorithm, and claim-specific causal evidence. For version drift, identify the changed behaviour and document attempts to recover the original environment. A failure to install the original version alone does not establish the size or cause of an output difference.

> Freeze a claim-specific variation protocol before candidate runs. Repeated executions must retain the same data, estimand, analysis, and named environment conditions, varying only the uncontrolled component under investigation. Use at least five independent executions for a stochastic source; use controlled version, platform, or scheduling comparisons for those sources. Record all attempts, settings, raw outputs, and the prespecified acceptance region. Do not select seeds, widen a range, or switch versions after seeing the candidate result. Published Monte Carlo error is usable only when its meaning, scale, coverage, and applicability to the target and comparison are established. A confidence interval for the substantive estimand is not a Monte Carlo error interval.

> Define `within_variation` by whether the printed value's rounding region is compatible with the frozen computational variation region, subject to the vetoes. For intervals, assess the endpoint pair jointly. A min-max range from a small set of runs is an operational acceptance rule, not a calibrated coverage guarantee. Record the chosen interpretation and its limitations.

I recommend that established computational variation take precedence over a lucky single-run printed match, with `printed_match` recorded separately. Otherwise a stochastic gold target may switch between `match` and `within_variation` depending on one candidate run. Under that recommendation, G-28 C3/C4 need the same variation adjudication as C6, even though their reference displays agree. Their unseeded computation is already acknowledged in the record and report (`model-gating/gold-set/gold/G-28.json:94-135`; [G-28 report](https://osf.io/download/6a83037a1926ed8280bb6617/), PDF pp. 5-6). If the lead instead intends `match` to take precedence, state that explicitly and retain their non-null variation records; they must not be recorded as deterministic.

> Missing gold evidence is an evaluator limitation, not a property of the study's computation. Quarantine an unresolved gold result from ranking until adjudication; do not label it `not_checkable` merely because the labellers lack a reference or variation envelope. A model's unsupported assertion of variation earns no `within_variation` credit. Its uncompleted attempt is recorded separately from a demonstrated scientific discrepancy.

This last distinction avoids forcing “not proven within variation” to mean “proven outside variation”. The draft currently specifies those two outcomes without a policy for insufficient evidence (`model-gating/benchmark/SPEC.md:136-138`).

### Sections 4.4-4.6

**AGREE with the settled fix rules. DISAGREE with the cross-track and aggregation gaps.** The prohibition on writing missing code is unqualified even though Track B requires writing an analysis. The translation category allows Stata into R or Python, whereas section 2's settled Stata policy specifies R. `recreated` has no outcome mapping, and multiple results sharing a claim ID have no claim-outcome aggregation (`model-gating/benchmark/SPEC.md:18-19,32,142-171`).

Proposed replacement:

> Track A permits only the listed fixes that leave the analysis unchanged. Translate Stata directly into R. Record a sequence of fixes, because a translation can also require path and dependency fixes. A skipped statement must be identified by source hash and location, with its error and the dependent-claim analysis showing why its output is not required. Track B permits newly written analysis code implementing the frozen documentary method and records `basis: recreated`; it does not permit changing the method to make the printed value recur.

> For each track, define a total status-by-basis table yielding the three settled claim outcomes. In Track B, a supported recreation with an accepted status maps to “reproduces”; documented admissible execution repairs map to “reproduces with justified fixes”. In both tracks, `discrepant` and `not_checkable` map to “does not reproduce”. Missing required evidence yields no score credit and an explicit attempt state. Define the claim outcome from all required result IDs, with failure taking precedence and fixes taking precedence over unmodified reproduction among successful results.

The scorer can mechanically check required fields and allowable combinations. Whether a claimed equivalent call or dependency explanation is true requires source or execution validation; it cannot be established by checking that a reason string exists (`model-gating/benchmark/SPEC.md:162-163`; `schemas/certificate.schema.json:89-95`).

Paper outcomes also need a decision table. Merely importing the rule pack leaves ambiguity between a partially blocked primary analysis, an unrelated script crash, and an underspecified Track B method. The reconciliation already distinguishes blockers on primary claims from blockers on some outputs (`model-gating/gold-set/reconciliation.md:14-19`), while the rule pack's descriptions are broader (`crowd-repro/RULEPACK-v1.1.0.md:93-100`).

> Predeclare primary claim IDs and paper-assessment scope. Successful primary computations with some discrepant or blocked dependent outputs imply computational issues. A demonstrated blocker preventing the primary computations implies technical failure. If all assessed results satisfy the accepted recurrence rules, report computationally reproducible. State how reporting slips and computational variation affect this decision. In Track B, distinguish underspecification, contradictory specification, unavailable data, and an executor's timeout in structured reasons; do not describe all of them as data failure. A paper judgement may draw on valid extra findings, but a judgement that contradicts the frozen must-check scope requires adjudication rather than automatic rejection.

For example, G-09's -0.665 can round to -0.67 under half-up, and G-10's 18.905 can round to 18.91; they do not require a looser tolerance (`model-gating/gold-set/gold/G-09.json:54-72`; `model-gating/gold-set/gold/G-10.json:50-70`).
- **Missing or coarsened references cannot establish strict full-precision reproducibility.** G-03 explicitly has no independent reference at the printed scientific-notation precision, and G-11 C2/C5 use a shipped log despite differing report-run diagnostics (`model-gating/gold-set/gold/G-03.json:32-57`; `model-gating/gold-set/gold/G-11.json:75-90`; `model-gating/gold-set/audit/v1.3/sol-review-r10.md:21-23`). I found no basis to invent new statuses for them. Freeze a gold-evidence policy that distinguishes label evidence from a numerical acceptance oracle, and require additional adjudication before rejecting a well-supported new run merely because it conflicts with a historical displayed reference. Do not automatically call those differences `within_variation` either.
- **Keep structural blockers ahead of variation explanations.** G-27's original pipeline remains blocked independently of its bootstrap randomness, and G-28's KSS claims remain blocked by the absent time column (`model-gating/gold-set/gold/G-27.json:258-262`; `model-gating/gold-set/gold/G-28.json:138-154`). The new variation status does not remove either blocker. Separately, audit G-24 against the newly explicit permission to skip independent failing statements: its record already notes that Table 1 expressions precede the parse fault, but contains no resulting values. This is a new execution-adjudication need, not grounds to invent matching results from static inspection (`model-gating/gold-set/gold/G-24.json:127-131`).

Replace the blanket statement that paper outcomes remain unchanged with a requirement to recompute them after adopting a single outcome policy. G-07's only scored discrepancy would become `close`, for example, while section 4.5 treats `close` as a successful claim outcome (`model-gating/gold-set/gold/G-07.json:32-146`; `model-gating/benchmark/SPEC.md:167-171,196-198`). Whether that paper still has computational issues must follow the explicit reporting-slip policy, not an inherited label.

### Track B gold

**DISAGREE with using Track A values as the default reference.** Track A evaluates executable deposited code, while Track B evaluates the published method. G-21 already supplies a concrete case in which the article-linked model and executable branch differ (`model-gating/benchmark/SPEC.md:16-19,157-160,200-204`; `model-gating/gold-set/gold/G-21.json:99-169`). G-22 supplies reporting slips for which a successful recreation should recover the analysis, not be tuned to the misprinted number (`model-gating/gold-set/gold/G-22.json:241-310`).

Proposed replacement:

> Build Track B gold from independent recreations using exactly the documentary corpus and sanitised data available to candidates. For each claim, specify the estimand, sample, exclusions, transformations, missing-data treatment, model, inference, and numerical conventions that the corpus determines. Two labellers work independently before inspecting Track A code, outputs, or reproduction reports. Execute and preserve their reference implementations and reconcile substantive differences. Track A results may corroborate a later adjudication, but do not define Track B truth.

> If multiple materially different implementations are consistent with the available description, record the exact missing choice, its documentary location, and at least two admissible implementations or a concrete demonstration that the choice changes the printed result. Freeze `underspecified` as a structured reason supporting `not_checkable`; require the candidate to identify the same substantive ambiguity, not merely use that status. Keep contradictory methods, missing data, and numerical failure separate. If multiple defensible implementations yield the same printed result, the claim need not be declared uncheckable. Exclude unresolved labeller disputes until adjudicated.

A model remembering public code remains a possible source of leakage even with network isolation. The current gold is explicitly a public development set, with public reports that models may have seen (`model-gating/gold-set/README.md:3-7,94-95`). Describe Track B as execution without supplied or retrieved author code, and avoid claiming absence of prior model knowledge. Ranking that depends on stronger blinding needs a separate held-out evaluation set.

## Section 6: scores and hard gates

**AGREE with paper-level macro-averaging and one headline per track. DISAGREE with status-only credit, unspecified failure handling, and the current hard-gate enforcement.** A correct `discrepant` string does not prove reproduction: it can accompany an unrelated computation. A correct `not_checkable` string needs no numeric code/log under the draft's hard gate and therefore offers an easy abstention strategy (`model-gating/benchmark/SPEC.md:211-230`). In the present scorer, correctness is literally status membership; `recomputed` is not checked for ordinary results (`model-gating/scripts/score_certificate.py:129-151`).

Proposed replacement:

> Before runs, freeze the target roster, scored result IDs, accepted evidence conditions, and weights. For each paper, average credit over its frozen must-check claims. Within a multi-result claim, average over the predeclared required result IDs so splitting a statistic into more output rows cannot change its weight. A result earns credit only if identification, scientific referent, admissible computation or evidenced blocker, analytical basis, required fix or variation evidence, and status all pass. Missing, failed, unsupported, and duplicate submissions earn no additional credit. A paper with a verified hard-gate violation scores zero.

> To include paper judgement in the complete-check measure, multiply that paper's result-based score by an indicator that its paper outcome is correct under the frozen aggregation and adjudication rules. The headline is the unweighted mean of these paper scores over all scheduled targets. Report claim-only accuracy and paper-outcome accuracy alongside it to show which part failed. Timeouts, missing certificates, and invalid certificates remain in the scheduled denominator with zero credit; infrastructure failures demonstrably outside the pipeline follow a predeclared rerun policy.

The multiplicative paper component is my proposed operational choice, not a settled requirement. If section 6 deliberately keeps paper outcome outside the headline, narrow section 1's definition to an end-to-end *claim-check* score and state that limitation explicitly. Do not call the present status-only quantity evidence of successful computational reproduction.

For deterministic `match`, verification compares an independently extracted executed value with the article. For `close`, it verifies the computation and supported slip. For `discrepant`, it verifies that the correct analysis actually differs under the rule; it need not force an alternative implementation's raw output to be bit-identical to a historical reference. For `not_checkable`, it verifies a specific dependency blocker or Track B ambiguity. For `within_variation`, it checks the frozen evidence conditions. Mechanical checks can validate structured data, hashes, and numerical predicates; source-level equivalence or underspecification needs adjudication unless a trusted reference test establishes it.

### Gaming and diagnostics

**DISAGREE that counting extra claims and auditing an unspecified random sample prevents gaming.** Flooding a certificate with true printed numbers gives more opportunities to overlap the must-check set, while only a sample of unscored rows is audited. Duplicate rows offering several statuses could also affect mapping unless the assignment is fixed before judgement (`model-gating/benchmark/SPEC.md:65-81,211-230`).

> Do not use submitted statuses or recomputed values to choose mappings. Require one final result per scientific identity, with contradictory duplicates invalid. Complete the same evidence checks for every row used for score credit. Define the extra-claim audit's sampling unit, seed, sampling rule, duplicate handling, adjudication, and resulting gate before running models. A copied paper number attached to the wrong scientific referent is not a valid identified claim. Consider an article-length-based submission budget, frozen independently of the hidden gold count, to bound indiscriminate enumeration. Report the number of extra findings and their audit results without treating them as false positives by default.

> Publish constant-status and abstention baselines under the identical mapping, evidence, and gate rules. Correctly evidenced abstentions earn credit on genuinely blocked gold; unsupported abstention does not. Specificity requires an identified, evidenced reproducing result, not merely the absence of the word `discrepant`. Missing and `not_checkable` outputs on reproducible gold are failures, not true negatives. Report all denominators and a status confusion matrix, alongside both binary and the settled three-way claim-outcome accuracy.

This specificity fix is necessary: the present scorer counts every status other than `discrepant`, including a missed claim, as specific on reproducible gold (`model-gating/scripts/score_certificate.py:160-163`). The draft's “claim outcome accuracy (reproduces vs does not)” also collapses the three settled outcomes and should be labelled as a separate binary diagnostic (`model-gating/benchmark/SPEC.md:167-171,219`).

### Gates, uncertainty, and dependence

> Restrict the “paper does not print” gate to an invented *reported target* or a materially false attribution after legitimate normalisation. Recomputed values, diagnostics, operational metadata, and intermediates are not required to occur in the article. Require a computational evidence bundle for attempted computations and source-backed evidence for blockers. Keep a trusted evaluator gate record with evidence, provenance, and adjudication status. Never infer fabrication from a numerical mismatch alone.

The draft's wording otherwise risks treating the purpose of recomputation as a violation (`model-gating/benchmark/SPEC.md:228-230`). The current scorer only reports schema errors and a narrow set of gates; it does not apply the proposed zero score or inspect external activity (`model-gating/scripts/score_certificate.py:118-151,214-228`). Schema validity also cannot establish that logged code really produced a value.

> Retain each twin's settled equal target weight in the point estimate, but resample independent paper families for uncertainty, keeping each original and its twin together. Use paired family resampling when comparing pipelines on the same targets. Publish original/twin and other prespecified component results as diagnostics without creating extra ranking headlines. State the actual number of eligible Track B targets after selection; do not promise a common target-count range in advance. Describe uncertainty as uncertainty for this development-set comparison, not population representativeness or protection against public-data contamination.

The original/twin relation is explicit in the manifests, and the current bootstrap resamples entries independently (`model-gating/gold-set/twins/README.md:5-20`; `model-gating/scripts/score_certificate.py:185-196`). The draft's claim that differences of a few points are noise is not established merely by a proposed target count (`model-gating/benchmark/SPEC.md:232-233`). Replace it with the actual interval and paired comparison when results exist.

## Section 7: modular pipeline and stage schemas

**AGREE with separating inputs, pipelines, and evaluation. DISAGREE that the current contracts permit interchangeable stages safely.** S2 lacks the article or methodological corpus that Track B needs, and S3 lacks the code, article context, and fix evidence needed to judge admissibility and inferential vetoes. The manifest puts model and executor at pipeline level even though the design promises different models and prompts per stage (`model-gating/benchmark/SPEC.md:249-275`).

Proposed replacement:

> Each stage consumes an immutable, versioned input bundle and declares the permitted artefacts and tools it can access. A model or executor may implement any stage, several combined stages, or the whole pipeline, but the boundary artefacts must validate against the same schemas and retain sufficient evidence for another pipeline to continue. Evaluation receives outputs and trusted input identities plus evaluator-only gold, mapping, and gate records. Model-authored stages never receive gold labels or twin metadata.

Minimum contracts:

1. **Input bundle.** Schema and benchmark versions; opaque target ID; track and mode; exact article/supplement/document hashes and versions; data and package manifest hashes; raw/processed starting scope; sanitisation recipe and removals in evaluator metadata; dependency and execution resources; permitted network/tool policy. End-to-end model bundles must not contain the gold `claims.json` even if it sits beside `target.json` in the evaluator's input store. The draft currently puts them in one directory (`model-gating/benchmark/SPEC.md:240-247`).
2. **S1 claims.** Stable claim and result IDs; article quote or table-cell locator with PDF and printed page references; study, model, sample, group, wave, contrast, and statistic identity; exact printed tokens; parsed operator, endpoints, units, precision, and scale; links among coefficient, uncertainty, and inferential assertions; explicit provenance for each selected target. Decomposed input uses the identical schema without labels or revealing rationale.
3. **S2 results.** Input hashes and result IDs; computation state such as completed, blocked, ambiguous, failed, or timed out; unrounded typed outputs and units, nullable only with a reason; source-code hash and line or expression references; execution command, environment, exit status, timestamps, and extractable log or machine-output locations; original and edited code plus ordered fix records; data and sample provenance; method choices and article evidence for recreation; full variation record and all repeated outputs. Do not require a guessed status at this stage. The current certificate instead makes `recomputed` a number or string even for uncomputed claims (`schemas/certificate.schema.json:82-95`).
4. **S3 judgement.** References to the same claims and S2 artefacts; status, basis, outcome, rule version, comparison calculation, named slip or blocker evidence, applicable nulls and thresholds, severity and its justification, variation decision, and paper outcome with scope. S3 must be able to inspect the pinned article, relevant code, execution evidence, and fix diffs. If those are only paths, the artefacts must be transferred with them and checked by hash. A semantic code or method audit cannot be performed from a scalar and a free-text reason alone.
5. **Trusted run record.** Stage DAG and artefact hashes; prompt contents and hashes; exact provider, model, options, executor and tool versions; resource budgets; stage and full-run time, token and cost accounting including failed attempts; retry/resume policy; trusted process/network audit; scheduled-target roster and final artefact selection. Preserve every attempt rather than selecting the best outcome after looking at gold.

These are minimum information requirements, not a requirement for a large framework. JSON schemas cover syntax and conditional fields; separate validators must cover ID uniqueness, referential integrity, allowed track/basis combinations, required evidence, endpoint ordering, and cross-file consistency. The present schema has no per-result identity or artefact-integrity contract (`schemas/certificate.schema.json:65-97,117-124`).

> Put `executor`, `model`, `options`, prompt, consumed artefact IDs, produced artefact IDs, and budget overrides on each stage, with explicit inheritance from pipeline defaults. Define how combined stages materialise intermediate artefacts and how the runner verifies the actual selected configuration. A judgement-only run on a frozen S2 bundle is a diagnostic pipeline, not an end-to-end reproduction score.

The existing runner always supplies the gold claims, skips an already collected certificate without checking configuration identity, shares an R library across runs, copies only certificate files, and builds its scoring CSV from collected certificates (`model-gating/benchmark/run_codex.py:30-41,59-79,92-99,123-130`). These are limitations of the pilot, not evidence that the proposed modular design is impossible. The replacement runner must preserve evidence bundles, isolate writable state, key reuse on input/pipeline hashes, and keep failed scheduled targets in evaluation.

### Section 7.4

**DISAGREE that an external working directory makes gold out of reach.** The existing README itself says this relies on the agent following instructions, whereas the spec states the stronger claim (`model-gating/benchmark/README.md:12-16`; `model-gating/benchmark/SPEC.md:278-282`). A different current directory is not a filesystem access boundary, and a model-authored command log is not an independent network audit.

> Use an isolated process environment with only the per-run input bundle mounted read-only, a fresh writable working directory, and explicitly permitted dependency access. Deny host repository, previous-run, home-directory, and credential access. Capture process execution and network activity in an evaluator-controlled record. Partition caches so one model or target cannot write evidence or results that another target can read. Apply the same isolation policy to all executors, and disclose any adapter that cannot enforce it.

## Section 8: implementation status

**AGREE with treating this as a specification for work still to be built. DISAGREE with proceeding directly from the listed artefacts to a ranking run.** The draft correctly identifies schema 1.2, stage contracts, mapping, Stata cases, and Track B gold as remaining work, but does not list the evidence adjudications, evaluator validation, or isolation enforcement identified above (`model-gating/benchmark/SPEC.md:284-293`).

Proposed replacement:

> Before ranking, freeze the revised rules, evidence-qualified gold, atomic result migration, paper-outcome aggregation, and Track B documentary corpus. Implement stage contracts, trusted evidence validation, mapping adjudication, denominator-preserving run accounting, and isolation. Validate the benchmark on representative boundary cases and adversarial submissions before the full run. Keep existing pilot results explicitly diagnostic and tied to their original prompt, gold, and package versions.

## Blocking objections

1. **Gold evidence and migration.** Resolve or exclude G-16's unsupported variation targets, G-28's unbounded variation targets, and G-29's seeded bootstrap targets. Apply one source-identified-slip standard to G-07, G-15, and G-22 C3. Replace G-21's scoring references when changing its labels. Freeze a policy for missing, coarse, and conflicting gold references. Details and citations are in section 5 above.
2. **Total comparison and outcome rules.** Specify typed printed values, precision and units, inequality and interval semantics, the bounded half-boundary convention, variation precedence and evidence, all status/basis combinations, and claim/paper aggregation. Resolve the Track B code-writing and Stata-language contradictions. Details and citations are in sections 3-4.
3. **Headline validity and anti-gaming.** Require verified computation or evidenced blockers for credit, settle the paper-judgement component or narrow the headline's stated scope, preserve all scheduled failures in the denominator, fix mapping and duplicate handling, and define extra-claim and gate audits. Correct specificity and use original/twin families for uncertainty. Details and citations are in section 6.
4. **Track B validity and leakage.** Freeze claim eligibility and the raw/processed-data boundary, audit retained contents, enforce mediated access, and build independent description-based gold rather than inheriting Track A answers. Details and citations are in sections 2 and 5.
5. **Interchangeable stages and real isolation.** Provide complete cross-stage evidence and identities, stage-specific configurations, trusted run records, isolated state, and enforceable filesystem/network boundaries. A working directory and prompt prohibition are insufficient. Details and citations are in section 7.

## Non-blocking suggestions

- Add concise worked examples from the existing gold for each comparison type, including negative rounding ties, a scientific-notation p value, a false non-p inequality, an exact count written as a word, a percentage-point effect, and a paired-cell reporting slip. The relevant cases are cited in sections 3-5.
- Publish development-set constant-status baselines and per-component diagnostic results beside the single headline. This helps interpret the status imbalance without reopening the settled single-score design.
- Report Track B eligibility exclusions and the added Stata cases separately so readers can see how the evaluated scope changes. Do not generalise from the development set to published research as a whole; its documented source concentration already limits that inference (`model-gating/gold-set/README.md:84-95`).
- Reconcile stale explanatory text when producing v1.4. For example, G-11 retains loose-tolerance and `close` language despite its frozen `match` status, and G-08 retains historical interpretations in explanatory fields (`model-gating/gold-set/gold/G-11.json:65-89,191-195`; `model-gating/gold-set/gold/G-08.json:123-144`; `model-gating/gold-set/claims/G-08.json:79`). This is documentation repair, not a request to reopen the agreed v1.3 interpretations.
