ReproCrowd benchmark: what it measures and how it runs

Specification draft 0.6 · 1 November 2026 · reviewed with GPT-6.1 Sol and Gemini 4 Argon · full specification

A ReproCrowd check is a statistical spell checker. A model extracts every reported number in a paper, reproduces each one from the authors' materials, and judges it. There are two tracks, with the authors' code and blinded without it, and each gets one end-to-end score. Your rulings on draft 0.4 are now in the specification. Sol and Argon each reviewed draft 0.5, and both of their sets of changes are applied in draft 0.6. In the round 5 confirmation, Argon agreed as drafted. Sol's one remaining point is applied exactly as Sol proposed it.

Needs your decision

before freezing1. The paper score formula

Paper score = extraction recall × average credit on the labelled results, halved if the paper outcome is wrong. A labelled number the model skips counts against both factors. If omissions alone bring both to 0.8, the product is 0.64. Both reviewers accept this as a deliberate penalty for incompleteness, and each paper still carries equal weight, however many numbers it prints.

Recommendation: accept. The alternative, recall and labelled credit as separate headline numbers, would break your "one score per track".

blocks ranking runs2. Isolation with the built-in macOS sandbox

Instead of Docker, each run would execute under sandbox-exec, the macOS sandbox that Codex itself uses:

  • Files: nothing is readable except system paths, the run's own folder and a read-only package library. That shuts out /Users, other volumes and the shared temp folders.
  • Login: HOME points into the run folder and holds a copy of only the login token, so earlier sessions stay invisible.
  • Network: everything is blocked except one local proxy. The proxy passes package repositories and the model's API, and checks that the provider's own web search is off.

A first test worked: R ran and loaded packages, while reading a gold file and connecting directly to CRAN both failed. The spec lists what an acceptance test must still show before ranking runs. Most importantly, the Codex and Claude Code command-line tools must work inside it with their own sandboxes switched off.

Recommendation: build the sandbox and its acceptance test as part of the runner work, with no install needed. Colima stays as the fallback if Codex or Claude Code won't run inside it.

3. Approve the order of work

  1. Gold v1.4:
    • exhaustive extraction of every reported number in all 30 papers, by two independent extractors with adjudication, which is the new big item;
    • the label changes below;
    • reruns for the held results.
  2. Rule pack 1.2, the public prompt and schema 1.2, published together.
  3. Runner and scorer: packages, sandbox, run records, evidence checks, and extraction matching.
  4. Adversarial tests of the scorer, for example copied values, misread and invented numbers, and all-not_checkable certificates.
  5. Stata papers: second-round screening is running (see below).
  6. Track B packages and gold.
  7. Full runs.

Recommendation: approve, and I start with the extraction protocol on two or three papers. That shows how long full extraction takes, and how often two extractors disagree, before committing to all 30.

Your rulings, as implemented

  • Every number is extracted. In scope is every printed number that reports a result computed from the data, anywhere in the article except the supplements. That includes estimates, standard errors in parentheses, intervals, p values, sample sizes and descriptives. Excluded are design numbers, significance asterisks, alpha thresholds, confidence levels, codings and indices.
    • Counting: each printed occurrence counts once, so a table value restated in the text counts twice, but one computation can serve both.
    • Gold extraction: two extractors match each other mechanically by table row and column labels, or by sentence. Every difference is adjudicated, and the list is frozen before any model runs.
    • The 15-claim cap is gone. The existing 5 to 8 labelled claims per paper carry the reproduction labels. A model's discrepancies on other numbers go to adjudication, which is how the labelled set grows.
  • close must be close. It needs both of these:
    • the printed value is one unit off in its last digit from the correctly rounded value (interval endpoints are checked one at a time);
    • an identified slip, such as truncation, explains it.
    A large deviation stays discrepant however obvious its cause. Every deviation is also labelled as explained (truncation, misrounding, transposition, copied cell, typo) or unexplained, and explanation accuracy is reported. The explanation must be demonstrable from the package and the run, because models may not read the human reports.
  • Misreading versus hallucination. The evaluator first finds which printed number, in the same paragraph or the same table row or column, the model's value came from.
    • If there is one, the case is a misreading: a decimal point, a digit, a sign, a percentage read as a proportion, or a neighbouring cell. It counts as not extracted and earns no credit.
    • If there is none, or the model reports a referent the paragraph or table doesn't contain, the case is a hallucination. One verified instance zeroes the paper.
  • Your other draft 0.4 rules stand, since you did not object: variation first, the paper outcome table, halving for a wrong outcome, and stripping outputs from every package.

Statuses

StatusWhen
matchRounding the recomputed value to the printed precision gives the printed value, by round-half-up or round-half-to-even. That is the only tolerance.
closeOne unit off in the last printed digit, with an identified slip. Vetoes still apply: a flipped sign, a changed null inclusion, a false printed bound or a crossed threshold is always discrepant. Counts must be exact.
within_variationThe analysis is not exactly reproducible (unseeded, or depends on an unrecoverable version, parallel order or optimiser), and the printed value lies in the range of repeated runs. The protocol is fixed in advance.
discrepantAny other difference, explained or unexplained. Severity follows the rule pack: P1 if it is a primary result, otherwise P2.
not_checkableA named blocker in the shipped code (P0), or (Track B) unavailable data or an underspecified method.

Fixes state the file, the lines, what changed and why the analysis is unchanged. The allowed kinds are path, package, exact equivalent call, script order, skipping a failing statement the result does not use, print-only statements, and translation. Writing missing analysis code, changing the specification or data, and switching on an option the authors describe but do not run are not fixes.

Scoring

  • Extraction recall: the share of gold numbers extracted with the exact token at the right place.
  • Result credit on labelled numbers (0 or 1): the number was extracted, its status is right, and its computation is verified. The evaluator checks the executed source and its diff, and the value must appear in the run's output. Where gold has a reference, both values must round alike. Copying the printed value earns nothing, and not_checkable needs the blocker named.
  • Paper score: recall × credit, halved for a wrong paper outcome. It is 0 for a hallucination, another hard gate, a timeout or an invalid certificate.
  • Headline: the mean over targets, one per track, with intervals that resample each twin together with its base paper.
  • Diagnostics:
    • extraction precision and misreadings;
    • explanation accuracy;
    • outcome accuracy and a confusion matrix;
    • sensitivity and specificity;
    • discrepancies on unlabelled numbers that survive adjudication;
    • nondeterminism recognised;
    • fix audit;
    • twins separately;
    • baselines that label everything match, not_checkable or discrepant;
    • cost.

Each stage runs in a fresh, sandboxed directory, with earlier stages' files mounted read-only at fixed paths, and its prompts need no filling-in. A pipeline is a short manifest naming the executor, model, options and prompt for each stage. One agent can do everything, or each stage can use a different model. Decomposed runs feed in the gold extraction to isolate reproduction and judgement. Executors are small adapters with one function signature, and the run record keeps every attempt, the configuration actually used, cost and a network log.

How the specification was agreed

Sol (GPT-6.1, high effort), round 1: "AGREE subject to the blocking changes listed". Five blocking objections:
  • labels that the evidence did not support;
  • incomplete comparison rules;
  • a headline that rewarded the status label without checking the computation;
  • a Track B design that left the authors' code reachable;
  • stage contracts too thin to swap pipelines, and isolation that was not enforced.
All five were taken up in draft 0.2. Review
Sol, round 2: two of the five objections resolved and three partly resolved. The changes Sol still required:
  • restore its conditional positions on G-07, G-15 and G-16;
  • fix the variation protocol before any model runs;
  • define the outcome for not_computed and for partial primary failure;
  • verify that the code actually computes each value;
  • apply one consistent fabrication rule.
All applied in draft 0.3, together with its non-blocking suggestions. Sol agreed with all four proposed rules. Review
Argon (Gemini 4, high), round 1: found the most practical gaps:
  • the sandbox can read the gold labels, which are also public;
  • twins could be recognised from their local path;
  • parallel runs share one R library;
  • bundles are not archived;
  • recomputed values are never compared with gold.
Two of its points were wrong against the code, and parts of its reply drew on stale context. Points and checks
Argon, round 2: run through the Antigravity command-line tool. Two delegated attempts had returned summaries written as if Argon were the spec's author, and an OpenCode attempt returned nothing. Its review was the most useful on implementation:
  • stage contracts that a second team could not build from;
  • flooding a certificate with genuine numbers to game recall;
  • shipped outputs that a model could copy from;
  • slip evidence that only the forbidden human reports contain;
  • provider-side web search bypassing the network proxy;
  • a credit rule that penalised recovering the original software version.
Adopted in draft 0.4, apart from two points it later accepted. Review

It also confirmed that stripping outputs breaks neither G-11, whose code does not read its log, nor G-22, whose code is extracted from the HTML first. Argon marked all its round 2 points resolved. Round 4, both, on your rulings (draft 0.5): both agreed subject to changes.
  • Sol: a counting unit for extraction; misreading and hallucination made mutually exclusive; the one-unit rule extended to intervals, percentages and p values; and a sandbox acceptance test before ranking. Sol checked G-08 C4, G-18 C1 and G-22 C1 against gold, and all pass the new close rule.
  • Argon: canonical locators two extractors can match; explicit exclusions such as asterisks and alpha thresholds; locators per result rather than per claim; evidence checks for explained discrepancies; severity restored; and a tighter sandbox (private HOME and temp folder, Unix sockets blocked, a reverse proxy for the model API, outside resource limits).
Where they differed, I kept captions and footnotes in scope, let compound transcription errors count as misreadings, and defined severity as in the rule pack. Sol · Argon
Round 5: Argon agreed as drafted and accepted all three of my choices. Sol accepted them too, with one remaining point: a value misread from an identifiable source must not also count as a hallucination. That is now fixed as Sol proposed. Sol · Argon
