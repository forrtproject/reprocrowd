ReproCrowd benchmark: what it measures and how it runs

Specification draft 0.3 · 1 November 2026 · reviewed with GPT-6.1 Sol and Gemini 4 Argon · full specification

The benchmark tests whether a model can identify a paper's key claims, reproduce them and judge them correctly. It has two tracks: with the authors' code, and blinded without it. Each track gets one end-to-end score. A claim earns credit only when the model shows the computation behind it, not just the right label. Each stage reads and writes fixed file formats, so any model, prompt or sequence of steps can be swapped in and scored the same way. Needs your decision

before freezing1. Four rules that Claude and Sol proposed, not yet seen by you

  1. Variation first. If an analysis is not exactly reproducible (for example an unseeded bootstrap), its result gets within_variation, even when one run happens to print the reported value. The aim is to reward noticing nondeterminism consistently. With the original seed and software versions recovered, the normal match rules apply.
  2. Paper outcome.
    • Computationally reproducible: every assessed result is match, close or within_variation. Reporting slips such as typos are listed, but the computation does not count as failed.
    • Technical failure: blockers prevent every primary computation.
    • Computational issues: anything in between.
  3. Paper outcome in the headline. A wrong paper outcome halves that paper's score. Sol first proposed setting it to zero, then agreed that halving keeps the claim work visible.
  4. Fabrication gate. Two or more values that the model says the paper prints, but which it does not, give the paper a score of 0. One instance is recorded but not penalised.

Recommendation: accept all four. The one with real consequences is rule 2: G-07 would probably move from computational issues to computationally reproducible, because its only discrepancy is now a typo identified by the source report.

Decisions to review

  • Stata goes to R only. You left R or Python to me. One target language keeps translations comparable.
  • No numerical ceiling on close. The old rule allowed a gap of up to 1 unit or 1%. Now close needs a demonstrated slip (truncation, transposed digits, swapped cells, or a typo located by the authors or a source), and undoing it must give an exact match. This answers your "why more?": rounding is the only tolerance for match, and close rests on evidence rather than size. As a result, G-07 C1 and G-15 C1 and C2 move from discrepant to close, and G-22 C3 stays close.
  • "Held" gold results. If the evidence does not yet support a label, the result is excluded from scoring until reruns settle it. It is not called not_checkable, because that would describe the study rather than our evidence.
  • Claim identification is recall of a must-check subset. The gold lists (5 to 8 claims per paper) are the claims the human sources assessed, not every important claim. The benchmark claims no more than that. Extra claims are audited, not penalised.
  • Track B gold is built independently by two labellers working only from the article and data, not copied from Track A. The published method and the shipped code can differ, as G-21 shows.
  • Twins count as one target each in the headline, but uncertainty intervals resample each twin together with its base paper.
  • Two of Argon's suggestions were not adopted. It proposed accepting both labels for G-21, which would reopen your decision. It also proposed accepting match for G-16 because the shipped .tex tables agree with the paper, but reading shipped output is not recomputation.

Claim statuses

StatusWhen
matchRounding the recomputed value to the printed precision gives the printed value, by round-half-up or round-half-to-even. That is the only tolerance.
closeA deterministic analysis where the printed value differs because of one demonstrated reporting slip, and undoing the slip gives a match. A flipped sign, a change in whether an interval contains the null, a false printed bound or a crossed threshold always counts as discrepant. Counts must be exact.
within_variationThe analysis is not exactly reproducible, and the printed value lies within the range of repeated runs. The causes are an unseeded random process, a seed whose random stream changed between versions, a package version that cannot be recovered, parallel order, or optimiser sensitivity. How many runs to do, and how the range is built, is fixed before any model runs.
discrepantAny other difference.
not_checkableThe value cannot be produced: a named blocker in the shipped code, or (Track B) unavailable data or an underspecified method.

Fixes. Every fix records the file, the lines, what changed and why the analysis is unchanged. The allowed kinds are:

  • path;
  • package install or pin;
  • exact equivalent call;
  • script order;
  • skipping a failing statement that the claim does not use;
  • translation.

Not allowed: writing missing analysis code, changing the model, sample or data, or switching on an option the authors describe but do not run (G-21).

Claim outcomes. Each claim reproduces, reproduces with justified fixes, or does not reproduce, as you specified.

Scoring

  • Result credit (0 or 1). The result must be identified, computed from the permitted inputs by admissible code, with the value traceable in the run's output, and given the right status. Where gold has a reference value, the recomputed value must equal it. So copying the printed value earns nothing, and a not_checkable earns credit only with the blocker named.
  • Paper score. The average over claims, halved if the paper outcome is wrong. It is 0 for a hard-gate violation, a timeout or an invalid certificate. Failed runs stay in the denominator.
  • Headline. The mean over all scheduled targets, one per track, with intervals from a bootstrap over papers (each twin resampled with its base paper).
  • Diagnostics alongside:
    • claim recall and outcome accuracy;
    • sensitivity and specificity;
    • a status confusion matrix;
    • nondeterminism recognised;
    • fix audit;
    • twins separately;
    • baselines that label everything match, not_checkable or discrepant;
    • minutes, tokens and US$ per target.

A pipeline is a short manifest naming the executor, model, options and prompt for each stage. One agent can do S1 to S3 in a single run, or each stage can use a different model. Decomposed runs feed in the gold claim list, or a frozen earlier stage, to isolate one step. Executors are small adapters for the Codex CLI, Claude Code, OpenCode, an API loop or a human. The run record keeps every attempt, the exact configuration used, cost and a network log.

How the specification was agreed

Sol (GPT-6.1, high effort), round 1: "AGREE subject to the blocking changes listed". Five blocking objections:
  • labels that the evidence did not support;
  • incomplete comparison rules;
  • a headline that rewarded the status label without checking the computation;
  • a Track B design that left the authors' code reachable;
  • stage contracts too thin to swap pipelines, and isolation that was not enforced.
All five were taken up in draft 0.2. Review
Sol, round 2: two of the five objections resolved and three partly resolved. The changes Sol still required:
  • restore its conditional positions on G-07, G-15 and G-16;
  • fix the variation protocol before any model runs;
  • define the outcome for not_computed and for partial primary failure;
  • verify that the code actually computes each value;
  • apply one consistent fabrication rule.
All applied in draft 0.3, together with its non-blocking suggestions. Sol agreed with all four proposed rules. Review
Argon (Gemini 4, high), round 1: found the most practical gaps:
  • the sandbox can read the gold labels, which are also public;
  • twins could be recognised from their local path;
  • parallel runs share one R library;
  • bundles are not archived;
  • recomputed values are never compared with gold.
